The frame an application sits in — header, footer, left navbar, right aside, and a
main area offset from all of them. Sizes go on the root as config and reach the
parts through CSS variables, so nothing is repeated.

Every region is optional. Leave one out and no space is reserved for it.

## Navbar sections

`AppShell.Section` divides the navbar. Exactly one section takes `grow` — it
absorbs the leftover height and scrolls, which pins whatever sits above and below
it. That's how a long link list keeps the account row visible at the bottom.

## Collapsing on small screens

Navbar and aside each hide below their own breakpoint — `md` and `lg` by default.
Below it, `opened` brings the region in over the content with an overlay that
dismisses on click or Escape.

A breakpoint is measured against **the shell's own width**, not the viewport's, so
a shell in a narrow column collapses even on a wide screen. The demo below asks for
`breakpoint="xl"` and the shell is nowhere near 1280px wide, so both regions are
already collapsed — press the buttons and they come in over the content.

<Preview>
  <Demo3 client:visible />
</Preview>

## Docking instead of floating

Below the breakpoint, `opened` floats the region over the content behind a scrim.
`mode="dock"` makes it take its space instead: `Main` insets around it, there's no
scrim, and it stays put until you close it — so a region can be a persistent part
of a narrow layout rather than a drawer you dismiss.

Both regions ask for `breakpoint="xl"`, which this shell is far short of, so they're
collapsed and `mode` is in play. Open one and flip the switch: `overlay` covers the
content, `dock` narrows it.

<Preview>
  <Demo4 client:visible />
</Preview>

```jsx
function Demo() {
  const [mode, setMode] = useState('overlay');
  const [nav, setNav] = useState(false);
  const [aside, setAside] = useState(false);

  return (
    <div className="space-y-3">
      <SegmentedControl
        label="Mode"
        value={mode}
        onChange={setMode}
        data={[{ value: 'overlay', label: 'overlay' }, { value: 'dock', label: 'dock' }]}
      />
      <div
        className="relative h-[320px] overflow-hidden rounded-lg border border-border"
        style={{ transform: 'translate(0)' }}
      >
        <AppShell
          header={{ height: 48 }}
          navbar={{ width: 160, breakpoint: 'xl', mode, opened: nav, onClose: () => setNav(false) }}
          aside={{ width: 160, breakpoint: 'xl', mode, opened: aside, onClose: () => setAside(false) }}
          padding="sm"
          className="min-h-full"
        >
          <AppShell.Header className="gap-2 px-2">
            <Button size="xs" variant="ghost" onClick={() => setNav((o) => !o)}>Nav</Button>
            <Button size="xs" variant="ghost" className="ml-auto" onClick={() => setAside((o) => !o)}>
              Aside
            </Button>
          </AppShell.Header>
          <AppShell.Navbar className="p-2 text-sm text-secondary">Navbar</AppShell.Navbar>
          <AppShell.Aside className="p-2 text-sm text-secondary">Aside</AppShell.Aside>
          <AppShell.Main>
            <p className="text-sm text-secondary">
              Main content. In <code>dock</code> it gets narrower; in <code>overlay</code> it stays
              put and the panel covers it.
            </p>
          </AppShell.Main>
        </AppShell>
      </div>
    </div>
  );
}
```

A docked region carries `data-mode="dock"`. `onClose` is still worth passing — it's
what your own toggle calls — but nothing dismisses a docked region for you, which
is the point: no scrim to click, and Escape is left alone so it can't yank a region
out of the layout from under the user.

### Where the room runs out

A region that reserves space is capped at `50cqw - 80px`, so it can never squeeze
`Main` below 160px however narrow the shell gets. Two 160px regions in an 830px
shell keep their full width and leave 510px; at 360px they shrink to 99px each and
`Main` still gets its 160px. The cap moves the region and the inset together, so
they can't drift apart and overlap.

| shell | navbar | aside | Main |
|---|---|---|---|
| 830px | 160 | 160 | 510 |
| 498px | 160 | 160 | 178 |
| 418px | 129 | 129 | 160 |
| 298px | 69 | 69 | 160 |

An `overlay` region is never capped — it floats over the content instead of taking
its space, so a 160px drawer stays 160px at any width. The cap is only about not
starving what's underneath.

## Props

### AppShell

| Prop | Type | Default |
|---|---|---|
| `header` | `{ height }` | — |
| `footer` | `{ height }` | — |
| `navbar` | `{ width, collapsedWidth?, collapsed?, breakpoint?, opened?, onClose?, mode? }` | — |
| `aside` | `{ width, breakpoint?, opened?, onClose?, mode? }` | — |
| `layout` | `default` `alt` | `default` |
| `padding` | `none` `xs` `sm` `md` `lg` `xl` | `md` |

Sizes take a number (px) or any CSS length. `navbar.breakpoint` defaults to `md`,
`aside.breakpoint` to `lg`. `collapsed` is inert unless `collapsedWidth` is set.
`mode` is `overlay` or `dock`, described above.

Breakpoints are container queries against the shell itself — `sm` 640, `md` 768,
`lg` 1024, `xl` 1280, the same numbers as Tailwind's screens. A shell that fills the
page behaves exactly as viewport breakpoints would; one in a split pane or a preview
card responds to the room it actually has. The root carries
`container-type: inline-size` to make that work, which does not affect the `fixed`
regions.

### Parts

`AppShell.Header` · `.Footer` · `.Navbar` · `.Aside` · `.Section` · `.Main` — each
takes its element's native props. `Section` takes `grow`. A part used outside an
`AppShell` throws rather than rendering something subtly wrong.

`useAppShellNavbar()` returns `{ collapsed, opened }`, which is how `NavLink`
knows to go icon-only. Use it for your own navbar content.

The regions are `fixed`, which is what keeps them still while main scrolls. To
contain the shell in a box rather than the viewport — as this page does — give the
wrapper a `transform`, making it the containing block for fixed descendants.
